#Mixback — frontend MVP (этап 3)
https://1lonx.github.io/mixback3/

Mixback — сервис фидбэка на сведение музыки: комментарии на таймкодах волны, версии микса, A/B-сравнение с выравниванием громкости по LUFS и чек-лист правок.

> Этап 3 итогового проекта. Сервера пока нет: данные хранятся в браузере (localStorage + IndexedDB) за интерфейсом, который на этапе 4 заменится HTTP-клиентом.

**Демо:** _ссылка появится после публикации (GitHub Pages, см. «Деплой»)_
**Демо-аккаунты:** `demo@mixback.app` (звукорежиссёр) и `artist@mixback.app` (артист), пароль `demo1234` — или кнопки «Быстрый вход» на странице входа.

## Что умеет MVP

| Сценарий | Путь |
| --- | --- |
| **Звукорежиссёр** | регистрация → создание проекта → загрузка микса (волна, LUFS и пик считаются в браузере) → приглашение артиста |
| **Артист** | открыть проект → сравнить версии (A/B без потери позиции, громкость выровнена) → оставить правку на нужной секунде |
| **Чек-лист** | правки группируются в задачи по категориям, пункты отмечаются |

Страницы: `/login`, `/projects` (поиск, фильтр, сортировка — в URL), `/projects/new`, `/projects/:id` (плеер, правки, чек-лист, участники, загрузка версии), `/projects/:id/edit`, `/profile`, `/about`, 404.

**Профиль** (`/profile`): аватар и статистика (с анимацией счётчиков), смена имени, смена пароля с индикатором надёжности, выбор темы, срок сессии, удаление аккаунта с подтверждением паролем.

**Темы и анимации.** Светлая и тёмная темы (плюс «как в системе»), выбор запоминается и применяется до первой отрисовки без вспышки; переключатель — в шапке и в профиле. Анимации на GSAP: переходы между страницами, каскадное появление карточек, живая волна на странице входа, счётчики; при `prefers-reduced-motion` всё отключается.

**Безопасность:** строгая CSP, очистка текста, проверка сигнатуры аудиофайла, PBKDF2, блокировка перебора пароля, срок сессии — подробно и с ограничениями в [SECURITY.md](SECURITY.md).

Состояния загрузки / пусто / ошибка есть везде. Их можно вызвать на странице «О проекте» → «Демо-режим» (медленная сеть, имитация сбоя).

## Запуск

Нужен Node.js ≥ 20.

```bash
cd client
npm install
npm run dev            # http://localhost:5173
```

| Команда | Что делает |
| --- | --- |
| `npm run check` | lint + prettier + typecheck + unit-тесты + сборка |
| `npm test` / `test:coverage` | Vitest + React Testing Library (порог покрытия 80/75/70) |
| `npm run storybook` | Storybook на :6006 |
| `npm run test:visual` | скриншотное сравнение всех stories (Playwright) |
| `npm run test:visual:update` | обновить эталоны после намеренных изменений |
| `npm run test:e2e` | E2E в Chromium на собранном приложении (+ axe-проверка доступности, мобильный вьюпорт) |

Первый раз для Playwright: `npx playwright install chromium`. Переменные окружения — в `client/.env.example`.

> Эталоны визуальных тестов лежат в `client/visual/stories.spec.ts-snapshots` с суффиксом платформы (`-win32`). На другой ОС их нужно сгенерировать командой `test:visual:update`; поэтому в CI визуальные тесты не запускаются.

## Архитектура

```
client/src
├─ api/            контракт MixbackApi + локальная реализация (localStorage/IndexedDB)
│  └─ local/       «сервер-на-клиенте»: права, валидация, HTTP-подобные ошибки, каскадное удаление
├─ app/            store, роутер, layout, типизированные хуки, apiThunk
├─ features/       auth · projects · project · comments · checklist · player · toasts
│                  (слайс + компоненты + тесты рядом)
├─ components/ui/  Button, Field (Input/Textarea/Select), Card, Badge, Dialog, States… + stories
├─ lib/            чистая логика: audio (peaks, LUFS BS.1770, gain), форматы, zod-схемы, чек-лист
└─ pages/          страницы (грузятся лениво)
```

**Ключевые решения**

- **Граница API.** Redux знает только интерфейс `MixbackApi` (передаётся в thunk через `extra`). На этапе 4 достаточно написать HTTP-реализацию с теми же методами и ошибками — слайсы, компоненты и тесты не меняются. Ошибки имеют HTTP-статусы (400/401/403/404/409), поэтому обработка уже «как с настоящим сервером».
- **Redux Toolkit.** `createAsyncThunk` через обёртку `apiThunk` (ошибки всегда сериализуемы), `createEntityAdapter`, мемоизированные селекторы. Защита от гонок: ответ на устаревший запрос игнорируется (`currentRequestId`). Оптимистичные «решено» и отметки чек-листа с откатом при ошибке. При выходе состояние сбрасывается целиком.
- **Валидация** — zod-схемы общие для форм и мок-сервера (на этапе 4 подключаются к Express).
- **Аудио.** Громкость считается по ITU-R BS.1770-4 (K-взвешивание, гейтинг) — проверено на контрольном сигнале EBU (−20 dBFS → −20 LUFS). Элемент `<audio>` умеет только ослаблять звук, поэтому выравнивание идёт к самой тихой версии. Плеер переживает смену версии и сохраняет позицию — так A/B честный.
- **Фильтры списка в URL** — ссылкой можно поделиться, «Назад» работает.
- **Доступность.** Семантика, подписи полей, `aria-live` для статусов и уведомлений, волна — `slider` с клавиатурой (←/→/Home/End/Space), нативный `<dialog>`, `prefers-reduced-motion`, axe-тест без серьёзных нарушений (WCAG A/AA).
- **Стили** — CSS Modules + дизайн-токены (палитра лендинга).

**Что намеренно упрощено до этапа 4**

- Пароль хранится как PBKDF2-хеш с солью, токен — случайная строка. Это защита от открытого текста, а не настоящая безопасность: argon2/bcrypt, JWT в HttpOnly-cookie и серверные лимиты — на бэкенде (см. SECURITY.md).
- Чек-лист строится правилами по ключевым словам (`lib/checklist.ts`); вместо него будет LLM с тем же форматом результата.
- Пик считается по выборкам (`peakDb`), а не true peak (нужна передискретизация) — это появится с ffmpeg на бэкенде. Поле `truePeak` из контракта этапа 1 временно называется `peakDb`.
- Аудио хранится в IndexedDB браузера, поэтому у каждого пользователя оно своё.

## Тесты

~480 unit/компонентных/интеграционных тестов (Vitest): редьюсеры и состояния async-операций, мок-API (CRUD, права, валидация, гонки записи), чистые функции (LUFS, пики, чек-лист, форматы, схемы), UI-компоненты и целые страницы через роутер. Плюс Storybook (24 stories) со скриншотным сравнением в обеих темах и E2E на Playwright (реальный Chromium, настоящее декодирование аудио, A/B во время воспроизведения, CSP, XSS, темы, профиль, axe в обеих темах).

`npm audit` сообщает о 4 moderate-уязвимостях в dev-цепочке Storybook (`glob`/`minimatch`); в production-сборку они не попадают.

## Маркетплейс (расширение этапа 3)

Mixback — это биржа услуг для звукорежиссёров: каталог `/engineers` (фильтры в адресе), профиль с услугами, портфолио-плеером и отзывами, заказы `/orders` и анкета `/profile/engineer`. Принятый заказ автоматически создаёт проект с версиями и правками на волне. Жизненный цикл заказа: ждёт ответа → в работе → сдан → завершён (или отклонён/отменён), отзыв оставляет заказчик после завершения. Оплата не подключена (этап 4+). Демо-аккаунты звукорежиссёров: ilya@, marina@, danil@, kira@mixback.app, пароль demo1234. У анкеты есть обложка: картинка сжимается в браузере (canvas, JPEG до 400 КБ) и хранится в моке как data:-URL; в каталоге показан счётчик опубликованных анкет.

**Чат по заказу.** На странице заказа есть переписка между заказчиком и звукорежиссёром (`messages.list/send`): Enter — отправить, Shift+Enter — перенос строки, новые сообщения подтягиваются раз в 5 с, в отклонённом/отменённом заказе чат только для чтения. Компонент `ChatView` не зависит от Redux, поэтому описан в Storybook (`Market/ChatView`, `Market/EngineerCard`, `Market/EngineerFilters`, `UI/Stars`, статусы заказов в `UI/Badge`).
